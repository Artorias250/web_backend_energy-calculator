## Окружение для лабораторной 4

В текущем окружении Redis установлен как служба Ubuntu/WSL. Приложение использует настройки `.env`:

```dotenv
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
SESSION_TTL_SECONDS=3600
SESSION_COOKIE_SECURE=false
FRONTEND_ORIGIN=http://localhost:5173
```

Проверка и запуск Redis в WSL:

```bash
sudo service redis-server start
redis-cli ping
```

Ответ должен быть `PONG`. Для просмотра сессий после входа:

```bash
redis-cli --scan --pattern 'session:*'
redis-cli GET 'session:<идентификатор>'
redis-cli TTL 'session:<идентификатор>'
```

Для Redis в WSL команда `docker exec` не нужна. В Docker Compose также предусмотрен необязательный профиль `redis-docker`: он нужен только при переходе с Redis в WSL на контейнер. Два сервера одновременно на порту 6379 запускать нельзя.

Остальные сервисы и приложение:

```bash
docker compose up -d
npm run start:dev
```

Swagger UI: [http://localhost:3000/api](http://localhost:3000/api). OpenAPI JSON: [http://localhost:3000/api-json](http://localhost:3000/api-json). В Swagger доступны параметры фильтрации, JSON-тела и загрузка `image`/`video` для шага «Далее». SSR-страницы исключены из документации API.

Используются TypeORM, PostgreSQL, `@nestjs/swagger`, `ioredis`, `cookie-parser` и `bcryptjs`. Пароли хешируются bcrypt с cost 12. Идентификатор сессии — случайные 32 байта в hex; Redis хранит `session:<идентификатор> → userId` с TTL, по умолчанию 3600 секунд. Cookie `sessionId` имеет `HttpOnly`, `SameSite=Lax`, `Path=/` и тот же срок жизни. Для HTTPS установите `SESSION_COOKIE_SECURE=true`. При повторном входе с прежней cookie она заменяется новой; при выходе запись Redis удаляется и cookie очищается.

`FRONTEND_ORIGIN` задаёт разрешённый origin SPA для CORS с credentials (несколько origin — через запятую). SPA должна отправлять запросы с `credentials: 'include'`. Swagger работает с cookie автоматически на том же origin.

Текущий пользователь определяется глобальным `SessionGuard`, а не константой. Все контроллеры защищены по умолчанию; декоратор `@Public()` разрешает каталог, ленту, регистрацию и вход. Публичные GET работают без cookie, с недействительной cookie и при недоступном Redis как для гостя. Защищённые запросы без сессии возвращают `401`, удаление чужого прибора — `403`, недоступное хранилище сессий — `503`. Сессия удалённого из БД пользователя не даёт доступ. SSR-черновик и все SSR-изменения также защищены; SQL-удаление ограничено владельцем.

У гостя `isOwner=0` и `isLiked=0`. После входа признаки вычисляются для пользователя из сессии. При создании `creator_id` заполняет сервер. Публикуется только собственный черновик, вернуть опубликованную карточку в черновик нельзя. Роли и дополнительные полномочия модератора не вводятся.

Postman и браузера достаточно для проверки API; дополнительные расширения редактора не требуются. При изменениях схемы БД не запускать `npm run migrate` на заполненной базе: этот скрипт пересоздаёт таблицы.

## Переход с лабораторной 3

Перед первым запуском ЛР4 на старой базе создайте резервную копию и выполните:

```bash
npm run migrate:lab4
```

Скрипт `scripts/lab4-passwords.ts` в транзакции преобразует старые открытые пароли в bcrypt-хеши, пропуская уже преобразованные. Он не меняет схему и не удаляет записи. Хеш занимает 60 символов и помещается в существующий `varchar(64)`. Почта и пароль для входа остаются прежними. Преобразование в текущем окружении уже выполнено; резервная копия находится в `backups/appliances-before-lab4.dump` и исключена из Git.

## Проверка лабораторной 4

1. В инкогнито откройте Swagger `/api`. Выполните GET списка с `minPower`, затем PUT публикации: без сессии ожидается `401`.
2. Выполните `POST /api/users/register` с уникальными `userName`, `email`, `password`, либо используйте существующую учётную запись. Регистрация не создаёт сессию.
3. Выполните `POST /api/users/login` с `email` и `password`. Ответ содержит публичные данные пользователя; cookie устанавливается через `Set-Cookie`. В Swagger не нужно вручную вводить cookie через Authorize: браузер отправляет её автоматически.
4. В DevTools → Application → Cookies → `http://localhost:3000` скопируйте значение `sessionId`. В Postman добавьте заголовок `Cookie: sessionId=<значение>` либо cookie через его Cookie Manager. Не копируйте атрибуты `HttpOnly`, `Path` и т. п. в заголовок запроса.
5. Выполните POST «Далее» с названием и файлами, GET своего черновика, PUT публикации с описанием и двумя числовыми полями. Ожидается успешная публикация с `formattedAt`.
6. Покажите ключ через `redis-cli --scan --pattern 'session:*'`, его `GET` (ID вошедшего пользователя) и `TTL`.
7. Проверьте ленту без ID, `?next=true`, лайки и удаление. Во втором аккаунте свой черновик; удаление чужого прибора возвращает `403`.
8. Выполните POST выхода. Повторите защищённый запрос со старой cookie: `401`. GET опубликованного списка со старой cookie и без неё продолжает возвращать `200`.

Коллекция `postman/lab4.postman_collection.json` содержит 17 запросов и проверки статусов. Укажите уникальные имя и email для регистрации, затем выберите файлы в запросе №6. Login сохраняет `sessionId`, «Далее» сохраняет `applianceId` в переменные коллекции. Cookie jar в запросах отключён, cookie передаётся явно: гостевые проверки не используют сохранённый вход. Можно вставить cookie из Swagger в переменную `sessionId` и пропустить login. При повторном выполнении регистрации для того же пользователя ожидается `409` — перейдите сразу к входу. Запрос удаления удаляет только карточку с ID из переменной `applianceId`.

## Автоматические проверки

```bash
npm test -- --runInBand
npm run test:e2e
npm run build
```

E2E-тест требует PostgreSQL с правом создания временной БД и работающий Redis. Он создаёт отдельную БД `lab4_test_*`, проверяет HTTP-сценарии двух пользователей, затем удаляет эту БД и только созданные тестом сессии. Рабочую БД не изменяет. MinIO в E2E подменён, поэтому тестовые медиа не попадают в рабочий бакет.

## Методы

| Метод | URL | Тело | Ответ |
|---|---|---|---|
| GET | `/api/appliances?minPower=` | — | Опубликованные услуги. `minPower` оставляет приборы с мощностью не ниже значения. Пустое значение или `0` показывает все. У каждой строки `isOwner`: `1`, если создатель совпадает с текущим пользователем, иначе `0` |
| GET | `/api/appliances/feed` | — | Первая опубликованная услуга, одна строка из базы. `isLiked`: `1`, если текущий пользователь её лайкнул, иначе `0` |
| GET | `/api/appliances/feed/:id?next=true` | — | Опубликованная услуга по id. `next=true` открывает следующую опубликованную после этого id |
| GET | `/api/appliances/draft` | — | Единственный черновик текущего пользователя. Если его нет, ответ `404` |
| POST | `/api/appliances` | `multipart/form-data`: только `applianceName` и файлы `image` и `video`, все три обязательны | Шаг «Далее»: создаёт черновик (`201`), описание, мощность и температура пока `null`. Если черновик уже есть, обновляет только название и файлы (`200`), сохраняя остальные поля. Имена файлов генерируются на латинице и записываются в `image_url` и `video_url`, сами файлы сохраняются в MinIO |
| PUT | `/api/appliances/draft` | JSON: `description`, `powerWatts`, `minTemperature` | Публикует черновик: статус становится `published`, заполняется `formatted_at` |
| DELETE | `/api/appliances/:id` | — | Мягкое удаление только своей услуги: статус становится `deleted`, заполняется `completed_at` |
| POST | `/api/appliances/:id/like` | JSON: `value` равен `0` или `1` | `1` ставит лайк текущего пользователя, `0` снимает его |
| POST | `/api/users/register` | JSON: `userName`, `email`, `password` | Новый пользователь без пароля в ответе, код `201` |
| POST | `/api/users/login` | JSON: `email`, `password` | Вход (`200`): публичные данные пользователя и `Set-Cookie: sessionId=…`; неверные данные — `401` |
| POST | `/api/users/logout` | —, cookie `sessionId` | Выход (`200`), удаление сессии Redis и очистка cookie; без действующей сессии — `401` |

Удалённые услуги в ответах не передаются. Вернуть услугу в черновик нельзя. Идентификатор, статус, создатель, модератор и даты в теле запроса не принимаются.

Ответ `POST /api/appliances` для шага «Далее» содержит только `id`, `applianceName`, `imageUrl` и `videoUrl`. Полный набор полей черновика доступен через `GET /api/appliances/draft`.

Публичны GET списка и ленты, а также POST регистрации/входа. Остальные API-методы требуют cookie `sessionId`.

## Таблицы

### users

| Поле | Тип | Ограничение |
|---|---|---|
| user_id | integer | первичный ключ |
| user_name | varchar(128) | уникальное, не пустое |
| email | varchar(64) | уникальное, не пустое |
| password | varchar(64) | bcrypt-хеш, не передаётся в ответах |

### appliances

| Поле | Тип | Ограничение |
|---|---|---|
| appliance_id | integer | первичный ключ |
| appliance_name | varchar(256) | не пустое |
| appliance_description | text | краткое описание |
| publication_status | varchar(32) | `draft`, `published` или `deleted` |
| image_url | varchar(512) | имя файла в MinIO |
| video_url | varchar(512) | имя файла в MinIO |
| power_watts | integer | мощность, Вт |
| min_temperature | integer | минимальная температура, °C |
| created_at | timestamp | дата создания |
| formatted_at | timestamp | дата формирования |
| completed_at | timestamp | дата завершения |
| creator_id | integer | внешний ключ на `users.user_id` |
| moderator_id | integer | внешний ключ на `users.user_id` |

У одного создателя не больше одного черновика.

### likes

| Поле | Тип | Ограничение |
|---|---|---|
| like_id | integer | первичный ключ |
| user_id | integer | внешний ключ на `users.user_id` |
| appliance_id | integer | внешний ключ на `appliances.appliance_id` |

Пара `user_id` и `appliance_id` уникальна. Каскадное удаление по внешним ключам запрещено.
